# v0.6.1 Release Notes

**Status: release candidate: not a published release.** Links in this file are relative to the
repository; the published release body pins them to the release tag.

## Release story

**v0.6.1 makes the message Broker a first-class, evidenced part of the architecture, without
guessing at anything the declarations do not say.**

A Service can now be reported as using a Broker, for example `rest-fights` using the Kafka cluster
`kafka:fights-kafka`, when (and only when) a declaration names a stable Broker id. A Broker says
which infrastructure a Service is declared to use. It never creates or implies a Queue, Topic,
Subscription, Message, producer or consumer, so the consumers of a topic stay unresolved exactly as
before.

## What's new

- **Broker entity and `USES_BROKER`.** Evidenced only by an explicit id: AsyncAPI `x-aip-broker-id`
  on an admitted Queue/Topic channel, or Architecture Manifest `brokers[].brokerId`. Namespace and
  virtual host are not identity. Missing, conflicting or ambiguous identity produces no Broker.
- **Answers.** `get_service_dependencies` (MCP and REST) returns a Broker claim; `get_evidence`
  resolves its evidence and exposes the Broker as a `broker` object.
- **Qualification.** Deterministic tests over the Azure Service Bus, Google Pub/Sub and Kafka
  fixtures, a Broker-only FinOS FluxNova/CALM transcription (two Services, one Broker, no
  destinations), a negative Apache Airflow boundary (no attribution to an unadmitted worker), and an
  independent reference for Broker and claim ids.
- **Quarkus Super Heroes demo:** a ninth walkthrough question, with the real answer and the explicit
  statement that the Broker does not resolve the missing consumer.

## What changed for integrators

**The public contract is data-dependent, not opt-in.** After a Service gains its first qualified
Broker claim, its `get_service_dependencies` answer moves from the v0.5 branch (`schema_version`
`"0.5"`) to the v0.6 branch (`"0.6"`); the same holds for `get_evidence` once a returned record
supports `USES_BROKER`. This is deterministic.
- A Broker-free answer keeps the unchanged v0.5 shape and still validates against the frozen v0.5
  schemas, so existing clients keep working for Services without Brokers.
- The MCP output schema for both tools is a `oneOf` discriminated by `schema_version`. A client that
  validates strictly against v0.5 must accept the v0.6 branch to read Broker-bearing answers.
- New schemas: `schemas/architecture_intelligence/v0.6/architecture-answer.schema.json` and
  `evidence-answer.schema.json` (no `v0.6.1` directory).

Unchanged: `get_architecture_drift` (always `"0.5"`), the locality tool, the REST deployments view
(`"0.5"`), exactly four MCP tools in the same order, `schemas/import/v0.5/*`.

Re-pins: AsyncAPI and manifest mapping rule version 2; snapshot canonicalization version 4. Inputs
with neither `x-aip-broker-id` nor `brokers[].brokerId` still produce an empty Broker set. The
release golden path and the runtime demo re-pin their snapshot to the Broker-bearing demo (49
nodes); see the [golden-path README](../../examples/release-golden-path/README.md#v061-re-freeze).
The pubsub fixtures' declarations are untouched; their Broker expectations live in sibling files.

## Known limitations

- A Broker is declared evidence only: no runtime observation, drift classification or locality
  qualification of Broker use. `destinationBrokerMappings` stays unimplemented.
- A Broker does not resolve a topic's consumers; `UNRESOLVED_IDENTITY` is unchanged.
- Cross-system evidence is deterministic fixtures and transcriptions, not a new real-world dossier.
- Historical v0.5.1 demo records (`docs/reference-integrations/glamorous-toolkit/0.5.1/*`) are
  untouched and describe the v0.5.1 answers.
