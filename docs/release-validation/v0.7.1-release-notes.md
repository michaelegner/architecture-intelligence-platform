# AIP v0.7.1 — Broker-Mediated Consumer Attribution

**Published as v0.7.1 on 2026-10-21** (terminal outcome `SHIPPED_VERIFIED`; see the
[release record](v0.7.1-release-record.md)). Links in this file are relative to the repository; the
published release body pins them to the release tag.

AIP adds the bounded question: **for one Kafka Topic in one broker and environment, which Services
can the evidence attribute as consumers, and with what qualification?** It is answered by a sixth
read-only MCP tool, `get_destination_consumers`, and by `POST /api/destination-consumers` and
`POST /api/destination-consumers/evidence`. There are exactly six read-only MCP tools. See
[`docs/mcp.md`](../mcp.md#get_destination_consumers-v071-i3).

## What an answer says, and what it does not

- **Two independent pieces of evidence.**
  - *Attachment:* a Kafka consumer group was attached to the Topic at capture time T, read from
    broker-held group state.
  - *Mapping:* an operator-supplied artifact maps that group to a declared Service.

  Only a `RESOLVED` row names a Service. `UNRESOLVED`, `AMBIGUOUS` and `CONFLICT` stay explicit and
  never mean "no consumer". A consumer group is never treated as a Subscription, and nothing is
  inferred from group names, client ids or hosts.
- **Attachment is not message processing.** It also does not mean the Service still consumes the
  Topic after T.
- **The list is never complete.** Every evaluated query is `PARTIAL` with `CAPTURE_SCOPE_LIMITED`:
  a capture covers only its configured consumer groups, at its own T. An empty or short list is not
  proof that nobody consumes the Topic.
- **Kafka only.** RabbitMQ was examined as a semantic contrast and stays source-specific. No
  RabbitMQ adapter ships, and a RabbitMQ Queue answers `DESTINATION_NOT_KAFKA_TOPIC`.
- **Evidence mode** resolves the answer's `destination-evidence:` refs at the same snapshot.
  `evidence_refs` must be duplicate-free and sorted in ascending order as plain strings. The schema
  can only state "unique"; the rule is in the tool description and in [`docs/mcp.md`](../mcp.md).

## Migration and contracts

Product, Producer and MCP server version become **0.7.1**. The five earlier tools, their answer
contracts and their meaning are unchanged. The new answer uses its own published `0.7.1` request
and answer schemas.

Two optional source types register the evidence (see [configuration](../configuration.md)):

```yaml
architecture_intelligence:
  sources:
    kafka_consumer_state:    # a normalized consumer-group capture (harness/kafka-capture)
      - {id: kafka-prod, root: ./captures/kafka, broker_id: kafka:prod, environment: prod,
         consumer_groups: [payment-service, ops-tail]}
    kafka_service_mappings:  # aip-kafka-consumer-service-mapping/1 artifacts
      - {id: kafka-prod-mapping, root: ./mappings/kafka, broker_id: kafka:prod, environment: prod}
```

Without these sources, the canonical snapshot has none of the new keys, so every earlier snapshot
is unchanged. **With Kafka consumer state, snapshot ids differ from v0.7.0**, because the declared
Topic brokers become part of the snapshot. As before, a snapshot id also depends on the absolute
paths of the declared source files, so ids are comparable only at one checkout location
([snapshot identity](../evidence.md)). The capture step is a repository harness, not part of the
image. Member ids, client ids and hosts are never stored, so none can be returned.

## Evidence and limitations

The expectations were written from stock Kafka CLI output and the application configuration, each
part before its own capture. They were then run twice on one exact commit, with byte-identical
results across the service, REST and negotiated MCP. The real-system replay used two captures of a
local [`ecommerce-system`](https://github.com/hungCS22hcmiu/ecommerce-system) deployment: one with
all consumers attached, and one after two of them had stopped. The release golden path replays the same package
against the image. See the [I4 result record](../specifications/0.7.1/i4-result-record.md) and the
[replay package](../specifications/0.7.1/i4-evidence/kafka/README.md). The product-value check is
**one coding-agent session** on one change (decision `CONTINUE`), not user research. In it, the
broker evidence surfaced a consumer group that code search could not find.

Known limitations:
- One real system, captured locally at two points in time. Ambiguous and conflicting mappings are
  covered only by synthetic tests.
- The capture allow-list needs upkeep: a group outside it is never seen.
- A namespaced Kafka Topic always answers `rows: []`, and an explicit-id Topic without a declared
  broker answers `BROKER_MISMATCH`.
- No RabbitMQ or other broker adapter, no hosted-demo update (that is v0.7.2), and no
  production-capacity claim.

Also in this release: the dev-only `certifi` dependency moves to 2026.10.19 (PYSEC-2026-4320),
and an external acceptance script for the public hosted Pitstop demo is added.
