**Status:** Draft, prepared during I4.1
(`docs/specifications/0.4.0/i4-release-candidate-publication-and-verification.md` §15). For use,
verbatim or adjusted, by I4.3 (`gh release create v0.4.0 --notes-file
docs/release-validation/v0.4.0-release-notes.md`) after the I4.2 GO decision and the `v0.4.0` tag
exist. Not itself a published release. The candidate identity below is a placeholder — I4.3 SHALL
fill in the exact GO commit SHA, not assume it is the current release-candidate.

**Evidence-link plan (spec §15/§29 — required before publication, not optional polish):** every
link below is written as a relative path for readability while this file lives in the repository.
Relative links do **not** reliably resolve inside a published GitHub Release body — the v0.3.0
release needed two rounds of review to catch and fix exactly this mistake (see that release's own
`v0.3.0-release-notes.md`). A single "use the GO commit SHA for every link" rule is not correct
either: the GO candidate SHA is a source-code identity, but `README.md`/`ROADMAP.md`/
`CHANGELOG.md`/this file/the GO record itself are all release-documentation surfaces that keep
changing *after* candidate freeze — a link into those files at the candidate SHA would point at
stale content that predates the very sections being linked. Before running `gh release create`,
I4.3 SHALL therefore resolve each link to one of three distinct identities, not one blanket SHA:

1. **Candidate/source identity** — the exact GO candidate SHA
   (`docs/release-validation/v0.4.0-go-no-go.md`'s named commit). Applies to: the Quick Start clone
   below (already tag-bound), and any link into source/config/schema files that ship as part of the
   tagged tree (e.g. `LICENSE`, `schemas/architecture_intelligence/v0.4/*.schema.json`).
2. **Fixed I1-I3 evidence identity** — the immutable commit where each I1/I2/I3 completion record
   was last finalized (unchanged by I4, since I4 does not reopen I1-I3's substantive content).
   Applies to: `docs/specifications/0.4.0/i1-completion-record.md`, the I2/I3 status entries in
   `docs/specifications/0.4.0/README.md`, and `docs/mcp.md`.
3. **Post-candidate documentation identity** — the immutable commit that actually contains the
   *final* version of a release-documentation surface that keeps evolving after candidate freeze.
   Applies to: `README.md`, `ROADMAP.md`, `CHANGELOG.md`, `SECURITY.md`, and
   `docs/release-validation/v0.4.0-go-no-go.md` itself — none of these exist in final form at the
   candidate SHA, so linking them there would be stale, not merely inconvenient.

For each category, I4.3 SHALL: replace the relative link with
`https://github.com/michaelegner/architecture-intelligence-platform/blob/<resolved SHA>/<path>`
using that category's identity (never `main`, which moves), then verify every resulting URL returns
`200` (e.g. `curl -sfo /dev/null -w '%{http_code}' <url>`) before publishing, not after. Record both
the candidate SHA and the post-candidate documentation SHA used, side by side, in the published
release body or in `v0.4.0-go-no-go.md`, so a reader can tell which identity backs which link.

This plan itself does not require the links to already be permalinks, and does not require picking
the post-candidate documentation commit now — this deliverable is the categorized plan and the
mandatory pre-publication resolve-and-verify step, not a premature guess at a commit that does not
exist yet.

## What v0.4 proves

> AIP v0.4.0 exposes the architecture intelligence validated through v0.3 as stable,
> snapshot-bound, evidence-backed, machine-consumable context for AI agents and architecture
> tools — through exactly three read-only MCP tools, deterministically qualified, with an agent
> never able to become the source of architectural truth.

`v0.3` proved AIP's architecture intelligence survives contact with real, independently authored
systems. `v0.4` does not add another architecture-intelligence dimension — it makes that already-
qualified intelligence safely consumable by external MCP clients: `get_service_dependencies`
(qualified one-hop dependencies), `get_architecture_drift` (only the declared-versus-observed
discrepancies — `OBSERVED_ONLY`/`NOT_OBSERVED_IN_WINDOW`, never a match), and `get_evidence`
(bounded, sanitized provenance resolution). Every answer is snapshot-bound, evidence-linked, and
explicitly qualified; nothing is invented, guessed, or silently absorbed.

## The three MCP tools

```text
get_architecture_drift      — direct dependencies whose evidence shows a declared-versus-observed
                               discrepancy, bound to one stable snapshot
get_evidence                 — resolves 1-20 opaque evidence references to sanitized provenance
                               for one explicit snapshot
get_service_dependencies    — one-hop direct dependencies, qualified against declared and
                               observed evidence, bound to a stable snapshot
```

`tools/list` always returns exactly these three, in this fixed lexicographic order. All three are
read-only (zero graph writes), require no LLM API key, and enforce closed input/output JSON
Schemas — see [`docs/mcp.md`](../mcp.md).

## The hero demo

An independent client — plain HTTP/JSON-RPC, no AIP internal module, no LLM — discovers all three
tools via `tools/list`, then calls `get_architecture_drift` for `service:order-service` and finds:

```text
OrderService -> LegacyPricingService     OBSERVED_ONLY   (never declared, real dependency)
OrderService -> unused-q                 NOT_OBSERVED_IN_WINDOW
```

then resolves the finding's evidence through `get_evidence` at the same snapshot. Reproducible from
a clean state in about five minutes, using fixed/frozen telemetry timestamps rather than a moving
window — see [`examples/runtime-demo/hero-demo.md`](../../examples/runtime-demo/hero-demo.md).

## Known limitations

- Direct dependencies only — no transitive dependency traversal.
- Current state only — no historical/point-in-time snapshots, no snapshot diffing.
- No generic Cypher/graph query surface through any tool.
- MCP is exposed for a local/trusted-network posture — not hardened for direct public-internet
  exposure, no authentication/authorization, no multi-tenancy.
- Every limitation already documented under `v0.3.0` (unsupported gRPC/Kafka-topic/database
  mechanisms, unresolved Airflow caller/runtime-role identity, insufficient-evidence Celery
  messaging identity) still applies — `v0.4` reuses that frozen evidence unchanged.
- Pre-1.0: Canonical Model, REST/MCP API surface, Graph Schema, Adapter SPI, and configuration
  format are not yet guaranteed stable.

None of the above represents an incorrect supported claim — each is explicit and bounded.
