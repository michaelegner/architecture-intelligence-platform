## Fixture topology and actual counts

One fixed target subgraph (`order-service` calling `product-service`'s `GET /products/{id}`, from
the real `examples/` fixture landscape, observed once) whose own structural shape is checked against
a frozen baseline before each scale point's unrelated filler is added
(`benchmarks.snapshot_read_cost._EXPECTED_TARGET_COUNTS`), plus N unrelated synthetic
Service/Operation/CALLS facts per scale point, seeded through the real production
`app.telemetry.aggregator.persist_observation_batch` write path.

| Scale index | Planned unrelated facts | Actual total nodes | Actual relations (total / `CALLS`) |
|---:|---:|---:|---:|
| 0 | 30 | 120 | 53 / 31 |
| 1 | 1,650 | 4,980 | 1,673 / 1,651 |
| 2 | 6,650 | 19,980 | 6,673 / 6,651 |
| 3 | 33,000 | 99,030 | 33,023 / 33,001 |

Every scale point's `structural_validation = PASS` (both the frozen target baseline and the planned
unrelated-fact delta matched exactly) and `semantic_validation = PASS` (the target
`get_service_dependencies` answer — claim identities, qualifications, delivery semantics,
limitations — was byte-identical across all four scale points, canonicalized to exclude only
snapshot identity/build metadata).

Total node/relation counts land in the same orders of magnitude the post-`v0.4.0` architecture
review used (`docs/architecture-review-0.4.0.md`) — ~10², ~5×10³, ~2×10⁴, ~10⁵ — confirmed by the
`total_nodes` column above, not merely planned.

```text
scale_index  total_nodes  snapshot_fingerprint_min_s  dependency_call_min_s
0            120          0.0353                       0.0900
1            4,980        0.3686                       0.4099

```

**Conclusion (bounded, per spec §16): observed cost increased with total graph size in this
environment.** This is not a claimed linear law, not extrapolated to a maximum safe landscape, and
not a production capacity claim — it is the measured shape of four samples in one environment. The
shape is directionally consistent with ADR 0011's own earlier ad hoc measurement
(`docs/adr/0011-snapshot-identity-read-cost.md`'s Context table), now reproduced through a committed,
schema-validated harness instead of an unrepeated developer-machine note.

## Target-answer invariance

`semantic_validation = PASS` at every scale point — the requested `get_service_dependencies` answer
for `order-service` (claim identities, qualifications, delivery semantics, limitations) remained
byte-identical while total graph/evidence size grew ~825× (120 → 99,030 nodes). Snapshot
identity/build metadata legitimately differed and was excluded from this comparison, per spec §12.

## Snapshot/model-revision consistency

`snapshot_id_consistent = true` and `model_revision_consistent = true` at every scale point — no
concurrent writer existed during any timed sample, and the revision fence did not move mid-sample
(verified; a fence move would have raised `RevisionFenceMoved` and failed the run rather than being
silently absorbed).

## Cleanup result

Each scale point wipes the disposable database before reseeding
(`benchmarks.snapshot_read_cost.wipe_database` — `MATCH (n) DETACH DELETE n`); the benchmark's own
Testcontainers Neo4j instance is torn down automatically when the CLI process exits. No developer or
shared database was touched at any point — the CLI always provisions its own disposable container.

## Explicit absence of performance/SLO qualification

No maximum-duration threshold exists in this release. A slower-than-`v0.4.0`-review absolute timing
is not, by itself, a release blocker — see spec §16/§30. This document reports measurements, not a
capacity or performance guarantee.

## Explicit absence of snapshot-cache or retention changes

No cache, incremental fingerprint, snapshot-identity change, or evidence retention/compaction policy
shipped in `v0.4.1`. `canonical_snapshot_state()`, `snapshot_fingerprint()`, and the stable-read
retry algorithm are byte-for-byte unchanged from what this benchmark measures — see
[ADR 0011](../adr/0011-snapshot-identity-read-cost.md)'s implementation/evidence note, which this
result satisfies the baseline half of.

## Determinism (smoke profile, spec §22 item 12)

Two clean `smoke`-profile runs from the same candidate SHA, in the same worktree, produced
identical deterministic structure under
`benchmarks.snapshot_read_cost.canonicalize_for_determinism()` — verified independently in Python,
