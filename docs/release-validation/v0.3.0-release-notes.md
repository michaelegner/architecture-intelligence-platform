# AIP v0.3.0 — Draft GitHub Release Notes

**Status:** Draft, prepared during I5.1 (`docs/specifications/0.3.0/i5-release-qualification.md`
§15). For use, verbatim or adjusted, by I5.3 (`gh release create v0.3.0 --notes-file
docs/release-validation/v0.3.0-release-notes.md`) after the I5.2 GO decision and the `v0.3.0` tag
exist. Not itself a published release. The candidate identity below is a placeholder — I5.3 SHALL
fill in the exact GO commit SHA, not assume it is the current `v0.3.0-rc.2`.

**Evidence-link plan (spec §12/§15 — required before publication, not optional polish):** every
link below is written as a relative path for readability while this file lives in the repository.
Relative links do **not** reliably resolve inside a published GitHub Release body — this is exactly
the mistake `v0.3.0-rc.1`'s release needed two rounds of review to catch and fix. A single "use the
GO commit SHA for every link" rule is not correct either: the GO candidate SHA is a source-code
identity, but `README.md`/`ROADMAP.md`/`CHANGELOG.md`/this file/the GO record itself are all
release-documentation surfaces that keep changing *after* candidate freeze (I5.1's own PRs already
demonstrate this) — a link into those files at the candidate SHA would point at stale content that
predates the very sections being linked. Before running `gh release create`, I5.3 SHALL therefore
resolve each link to one of three distinct identities, not one blanket SHA:

1. **Candidate/source identity** — the exact GO candidate SHA
   (`docs/release-validation/v0.3.0-go-no-go.md`'s named commit). Applies to: the Quick Start clone
   above (already tag-bound), and any link into source/config files that ship as part of the tagged
   tree (e.g. `LICENSE`).
2. **Fixed I4 evidence identity** — the immutable commit where each I4 dossier document was last
   finalized (unchanged by I5, since I5 does not reopen I4's substantive content). Applies to:
   `docs/real-world-validation/cross-system/report.md`, `.../revalidation.md`,
   `.../finding-ledger.md`, and `docs/specifications/0.3.0/`.
3. **Post-candidate documentation identity** — the immutable commit that actually contains the
   *final* version of a release-documentation surface that keeps evolving after candidate freeze.
   Applies to: `README.md`, `ROADMAP.md`, `CHANGELOG.md`, `SECURITY.md`, and
   `docs/release-validation/v0.3.0-go-no-go.md` itself — none of these exist in final form at the
   candidate SHA, so linking them there would be stale, not merely inconvenient.

For each category, I5.3 SHALL: replace the relative link with
`https://github.com/michaelegner/architecture-intelligence-platform/blob/<resolved SHA>/<path>`
using that category's identity (never `main`, which moves), then verify every resulting URL returns
`200` (e.g. `curl -sfo /dev/null -w '%{http_code}' <url>`) before publishing, not after. Record both
the candidate SHA and the post-candidate documentation SHA used, side by side, in the published
release body or in `v0.3.0-go-no-go.md`, so a reader can tell which identity backs which link.

This plan itself does not require the links to already be permalinks, and does not require picking
the post-candidate documentation commit now — WP7's deliverable is the categorized plan and the
mandatory pre-publication resolve-and-verify step, not a premature guess at a commit that does not
exist yet.

## What v0.3 proves

> AIP v0.3.0 proves that the architecture intelligence validated reproducibly in v0.2 survives two
> independently authored real systems — an external reference architecture and mature real-world
> OSS software — and hardens the Canonical Model only where real evidence justifies it.

`v0.2` proved AIP's architecture intelligence behaves correctly against known, hand-authored
ground truth. `v0.3` does not add another architecture-intelligence dimension — it tests the same
model against systems AIP's own authors did not build: Quarkus Super Heroes (a controlled,
externally authored microservice reference architecture) and Apache Airflow (a mature real-world
system with API server, scheduler, workers, and asynchronous task execution). The result is
deliberately bounded, not a claim of complete conformance: supported claims are materially
correct, unsupported mechanisms remain explicit, unresolved identity is never guessed, and
non-observation is never treated as absence.

## Known limitations

- gRPC/protobuf calls (Quarkus) — unsupported.
- Kafka topic/subscription semantics (Quarkus) — unsupported.
- `messaging.operation` legacy-attribute recognition gap (Quarkus) — insufficient evidence,
  deferred.
- PostgreSQL/database dependencies (Airflow) — unsupported.
- Airflow Execution API caller identity — unresolved by design, not guessed.
- Airflow runtime-role / Celery messaging identity — unresolved, deferred.
- Pre-1.0: Canonical Model, REST API, Graph Schema, Adapter SPI, and configuration format are not
  yet guaranteed stable.

None of the above represents an incorrect supported claim — each is explicit and bounded.

it must never become the source of architectural truth. See [`ROADMAP.md`](../../ROADMAP.md) for
the full v0.4 → v0.5 → v0.9 → v1.0 sequence.
