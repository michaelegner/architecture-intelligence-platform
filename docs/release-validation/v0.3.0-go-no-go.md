Three open code-scanning alerts on `refs/tags/v0.3.0-rc.2` at review time:

| Alert | Package | Trivy severity | Classification |
|---|---|---|---|
| `CVE-2026-59890` | `setuptools` (referenced version `70.3.0`) | MEDIUM | `KNOWN_LIMITATION` — not release-blocking |
| `CVE-2025-47273` | `setuptools` (referenced version `70.3.0`) | HIGH | `KNOWN_LIMITATION` — not release-blocking |
| `GHSA-6v7p-g79w-8964` | `msgpack` (referenced version `1.1.2`) | HIGH | `KNOWN_LIMITATION` — not release-blocking |

**Independently verified inside the actual pulled GHCR image** (not inferred from the alert text):
neither package is importable in the app's venv Python nor the base-image system Python —
`python -c 'import setuptools'` / `import msgpack` both raise `ModuleNotFoundError`. Both version
strings originate solely from pip's own bundled `_vendor/vendor.txt` and `_vendor/bom.cdx.json` —
an SBOM/vendoring-policy manifest pip ships describing what it vendors, not an installed or
importable package. `msgpack` additionally exists only as inert vendored *license* text
(`pip-*.dist-info/licenses/src/pip/_vendor/msgpack`), never as executable code. The running
`uvicorn app.main:app` process never invokes pip, setuptools, or msgpack at runtime. Trivy's Python
package scanner is parsing pip's own vendoring manifest as if it listed installed dependencies —
none of the three referenced versions are present as reachable code in this image. This is a
base-image (`python:3.13-slim`'s bundled `pip`) characteristic, not something this project's own
dependency pins control.
