prepared during I4.1`, the multi-paragraph evidence-link resolution *instructions*, and the
placeholder `Candidate SHA: <filled in by I4.3 at GO...>` block, never actually replaced with the

Quick Start, known limitations, what changed since v0.3.0, what's next, documentation, security),

## Trivy review — corrects an I4.2 verification gap

**I4.2's `v0.4.0-go-no-go.md` incorrectly reported "zero open code-scanning alerts of any kind"**
for `v0.4.0-rc.1`. That query (`gh api .../code-scanning/alerts`) was not scoped by `?ref=`, so it
only surfaced alerts associated with the default-branch scan context and missed the
release-image-scoped Trivy alerts entirely. Re-run correctly here, scoped to the actual tag:

```bash
gh api "repos/.../code-scanning/alerts?ref=refs/tags/v0.4.0-rc.1"   # already open, same alert numbers
gh api "repos/.../code-scanning/alerts?ref=refs/tags/v0.4.0"        # confirmed below
```

Three open code-scanning alerts on `refs/tags/v0.4.0` (and, on inspection, already present on
`refs/tags/v0.4.0-rc.1` since 2026-08-27 — i.e. these predate I4 entirely and were never new):

| Alert | Package | Trivy severity | Classification |
|---|---|---|---|
| `CVE-2026-59890` | `setuptools` | MEDIUM | `KNOWN_LIMITATION` — not release-blocking |
| `CVE-2025-47273` | `setuptools` | HIGH | `KNOWN_LIMITATION` — not release-blocking |
| `GHSA-6v7p-g79w-8964` | `msgpack` | HIGH | `KNOWN_LIMITATION` — not release-blocking |

**Independently verified inside the actual pulled `v0.4.0` GHCR image** (not inferred from the
alert text, and not assumed from v0.3.0's own investigation): `python -c 'import setuptools'` /
`import msgpack` both raise `ModuleNotFoundError` in the app's venv Python. The only filesystem
traces of either name are `pip`'s own vendored `_vendor/msgpack` directory and license text
(`pip-*.dist-info/licenses/...`) — an SBOM/vendoring manifest pip ships describing what it
vendors, never installed or importable application code. This is the identical disposition
`v0.3.0-go-no-go.md`/`v0.3.0-post-release-verification.md` already established for the same three
alert numbers — a base-image (`python:3.13-slim`'s bundled `pip`) characteristic, not something
this project's dependency pins control, and not a regression introduced by `v0.4.0`.

```text
Known critical release-blocking security findings = 0
Unreviewed release-blocking image findings        = 0
```

This does not change I4.2's or I4.3's GO decision — the disposition is identical to what would
have been recorded had the ref-scoped query been run correctly the first time, and matches the
already-accepted `v0.3.0` precedent exactly. It is recorded here as a correction to I4.2's
methodology, not a new finding requiring a release blocker under spec §31.
