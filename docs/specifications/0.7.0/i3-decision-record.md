## D3 — Request vocabulary (I3 §4)

Query request (`mode: "query"`):

| Field | Frozen decision |
|---|---|
| `target` | Required object `{kind, id}`. `kind` ∈ `APPLICATION_SERVICE`, `API_OPERATION`, `GATEWAY_ROUTE`. `id` is exact: `^service:` (canonical Service id), `^operation:` (canonical Operation id) or `^gateway-route:owned:[0-9a-f]{64}$` (`GatewayRoute.id`), 1–512 characters. Never a display name, path or host. |
| `gateway_instance_id` | Required, 1–256 characters, no leading/trailing whitespace, no control characters. The operator-declared value, matched exactly. |
| `environment` | Required, the existing `ENVIRONMENT_PATTERN`, ≤ 128 characters. Matched exactly. |
| `window_start`, `window_end` | Required, whole-second UTC `YYYY-MM-DDTHH:MM:SSZ` (the I2 form). Matched exactly against the stored window strings. **No ordering check:** an I2 window with `window_start >= window_end` is an accepted-but-invalid window (`GWM_WINDOW_ORDER_INVALID`) and must stay addressable, so a reversed pair is not a validation error. |
| `consumer_id` | Optional, `^gateway-consumer:owned:[0-9a-f]{64}$`. An exact `GatewayConsumer.id` filter on rows, not a username search. A consumer that is not in the selection simply yields no rows. |
| `limit` | Optional integer 1–200, default 100. |
| `cursor` | Optional opaque continuation (D8). |
| `snapshot_id` | Optional on a first query (`SNAPSHOT_ID_PATTERN`): an assertion that the latest snapshot is this one. Required with `cursor` (a cursor already names its snapshot; a mismatch between the two is `SNAPSHOT_NOT_AVAILABLE`). |

Evidence request (`mode: "evidence"`): `snapshot_id` (required), the same context fields as the query (`target`, `gateway_instance_id`, `environment`, `window_start`, `window_end`, optional `consumer_id`, **no** `limit` or `cursor`) and `evidence_refs[1..20]`, sorted, distinct, each `^api-evidence:[0-9a-f]{64}$`.

Malformed shape, pattern or range is a validation error (REST 422, MCP validation error). A well-formed request that names an unknown target, a window that does not exist or a stale snapshot is a typed refusal (D6).

## D4 — Answer payload (I3 §§5–6, §11)

`mode: "query"` `data` (`ApiConsumerUsageData`), field names frozen, I3.1b fixes types:

| Field | Content |
|---|---|
| `request_context` | The normalized request without `limit`, `cursor` and `snapshot_id`: `target`, `gateway_instance_id`, `environment`, `window_start`, `window_end`, `consumer_id` (omitted when absent). |
| `window` | `window_start`, `window_end`, `source_instance_id`, `valid` (true iff the I2 `window_reasons` are empty), `reasons[]` (the sorted I2 window reasons, `GWM_WINDOW_*` / `GWM_VERSION_INCOMPATIBLE`), `evidence_refs[]` (the `MEASUREMENT_WINDOW` ref, D9). |
| `rules` | `reconciliation` and `qualification`, each `{rule_id, rule_version}` from the snapshot. |
| `association_summary` | Present for `API_OPERATION` (`route_operation`) and `APPLICATION_SERVICE` (`target_service`), omitted for `GATEWAY_ROUTE`. Each is `{resolved_to_target, resolved_elsewhere, unresolved, ambiguous, conflict}`, the counts of **all GatewayRoutes in the selected gateway/environment scope** by the I2 outcome of that chain, before target filtering (I3 §5.2, §5.3). They sum to the scope's Route count. Informational only. |
| `selected_routes` | One entry per Route selected by the target, sorted by `route_id`: `{route_id, source_route_id, coverage, limitations[], evidence_refs[]}`. `coverage` is the I2 `coverage` value; `limitations` are its sorted I2 codes; `evidence_refs` is the route's `QUALIFICATION_LIMITATIONS` ref when `limitations` is non-empty. It is emitted independently of `rows`, so `rows: []` never hides an invalid window or an `UNKNOWN_COVERAGE` Route. |
| `configuration_sources` | One entry per APISIX configuration source in scope, sorted: `{gateway_instance_id, environment, source_revision}` from `gateway_configuration_v1.source_evidence`. |
| `measurement_sources` | One entry per measurement source in scope, sorted: `{source_instance_id, window_start, window_end, apisix_version}`. (Today exactly one: single gateway, single window.) |
| `rows` | `qualification_rows` entries, enriched (below), ordered by `(consumer.id, gateway_route.id)`. |
| `page` | `{limit, returned, next_cursor?}`. |

**Row** (`rows[]`; one I2 `qualification_rows` entry, nothing recomputed):

| Field | Content |
|---|---|
| `consumer` | `{id, source_name}`: the `GatewayConsumer.id` and the APISIX username, labelled source-qualified (D7). |
| `gateway_route` | `{id, gateway_instance_id, source_route_id}`. |
| `api` | `reconciliation`: the I2 `route_operation` outcome of the row's Route; `operation_id?`; `contract_version_reconciliation?` and `contract_version_id?`, `contract_id?` present only when the Operation is `RESOLVED` (I2 evaluates the contract chain only then). |
| `application_service` | `{reconciliation, service_id?}` from the independent I2 `target_service` outcome. |
| `configured_access` | `{status}`. |
| `usage` | `{status, coverage, upstream_request_count?, rejected_attempt_count?, interaction_id?}`; the counts are omitted, never zero, when I2 omits them (invalid window); `interaction_id` is present iff I2 has an interaction for the pair and is an opaque row-local value, not resolvable by any evidence mode. |
| `evidence_refs` | Sorted, distinct D9 refs. |
| `limitations` | The sorted I2 row limitation codes. |

**Selection (I3 §5).** `GATEWAY_ROUTE`: the Route with that id, if it belongs to the requested gateway and environment. `API_OPERATION`: the Routes of the scope whose I2 `route_operation.operation` is `RESOLVED` to the requested Operation. `APPLICATION_SERVICE`: the Routes whose independent `target_service.target` is `RESOLVED` to the requested Service. Rows are the I2 `qualification_rows` of the window whose Route is selected (and whose consumer matches `consumer_id`, if given). Nothing else is attached to a target.

## D6 — Outcomes and limitation codes (I3 §§4, 8, 11)

Envelope limitation codes (closed enum, separate from the 0.5 `LimitationCode` and the 0.6 locality enum; a limitation is `{code, message}`):

`SNAPSHOT_NOT_AVAILABLE`, `MEASUREMENT_WINDOW_NOT_AVAILABLE`, `UNKNOWN_TARGET`, `TARGET_NOT_IN_WINDOW_SCOPE`, `CURSOR_QUERY_MISMATCH`, `NO_ROUTE_SELECTED`, `MORE_ROWS_AVAILABLE`, `WINDOW_NOT_VALID`, `COVERAGE_UNKNOWN`, `EVIDENCE_REF_NOT_RESOLVED`.

**Envelope invariant.** `data` is null **if and only if** the answer is a *refusal*: a pre-evaluation failure, `NOT_ANSWERED`, with exactly one of the five refusal codes below. `NOT_ANSWERED` does not imply a null `data`: an *evaluated* answer with a negative or empty semantic result is also `NOT_ANSWERED` but carries `data` and its own non-refusal code (`NO_ROUTE_SELECTED`; in evidence mode `EVIDENCE_REF_NOT_RESOLVED` with every entry `NOT_RESOLVED`). I3.1b encodes both directions as validators and, where expressible, as a schema if/then keyed on the code: null `data` ⇒ `NOT_ANSWERED` and exactly one refusal code; a refusal code ⇒ null `data`; a non-refusal code with null `data` is invalid.

A **refusal** evaluated nothing: `data` is null, `outcome` is `NOT_ANSWERED` and `limitations` has exactly one code, one of the first five above. The set is mode-specific: **query** can refuse with all five; **evidence** can refuse with the first four only, because the evidence request has no `cursor`, so `CURSOR_QUERY_MISMATCH` is query/continuation-only and unreachable in evidence mode.

| Situation | Outcome | Code | `data` |
|---|---|---|---|
| Malformed request | — (REST 422 / MCP validation error) | — | — |
| `snapshot_id` or cursor snapshot is not current, or the read is unstable | `NOT_ANSWERED` | `SNAPSHOT_NOT_AVAILABLE` (current `SnapshotRef` when known, else `snapshot: null`) | null |
| No `api_usage_v1` window for `(gateway_instance_id, environment, window_start, window_end)`, including a configured gateway without an accepted measurement source | `NOT_ANSWERED` | `MEASUREMENT_WINDOW_NOT_AVAILABLE` | null |
| Target id is not a known canonical Service, Operation or `GatewayRoute` in the snapshot | `NOT_ANSWERED` | `UNKNOWN_TARGET` | null |
| `GATEWAY_ROUTE` target exists but belongs to another gateway/environment than requested | `NOT_ANSWERED` | `TARGET_NOT_IN_WINDOW_SCOPE` | null |
| Cursor is well-formed but bound to different request inputs | `NOT_ANSWERED` | `CURSOR_QUERY_MISMATCH` | null |
| Known Operation/Service target, no Route of the scope resolved to it | `NOT_ANSWERED` | `NO_ROUTE_SELECTED` | present: empty `selected_routes` / `rows`, `association_summary` shows why |
| Evaluated; more rows beyond this page | `PARTIAL` | `MORE_ROWS_AVAILABLE` | present, `next_cursor` set |
| Evaluated; the window has reasons | `PARTIAL` | `WINDOW_NOT_VALID` | present, `window.valid = false` |
| Evaluated; ≥ 1 selected Route is `UNKNOWN_COVERAGE` | `PARTIAL` | `COVERAGE_UNKNOWN` | present |
| Evaluated; none of the above | `ANSWERED` | — | present |

- Refusals are evaluated in table order (snapshot, then window, then target, then cursor; evidence mode has no cursor step), so a request with several defects gets one deterministic code.
- Several `PARTIAL` codes can hold at once; `limitations` is the sorted set of exactly the codes the data implies (a validator in I3.1b, as v0.6 D9).
- A row-level or Route-level `UNRESOLVED` / `AMBIGUOUS` / `CONFLICT` association never changes the outcome: it is explicit in the row and the summary (I3 §7). `USAGE_UNESTABLISHED` is likewise a row fact, not a limitation.
- Empty `rows` with a known selection is `ANSWERED` or `PARTIAL` by the rules above, never `NOT_ANSWERED`.
- Evidence mode: `ANSWERED` when every ref resolves, `PARTIAL` with `EVIDENCE_REF_NOT_RESOLVED` when some resolve, `NOT_ANSWERED` with `EVIDENCE_REF_NOT_RESOLVED` (data present, every entry `NOT_RESOLVED`) when none does. The same first four refusals (snapshot, window, unknown target, target outside the window scope) apply before any ref is looked at; `CURSOR_QUERY_MISMATCH` does not exist in this mode.

## D7 — Consumer and credential exposure (I3 §6.2)

- `consumer.source_name` is the APISIX Consumer `username`, exposed exactly and labelled in the field description and the MCP description as **source-qualified** (an APISIX identity on one gateway instance), not an application or person identity. It appears only in `rows[].consumer` and in `CONFIGURED_ACCESS` evidence.
- The schemas contain **no** credential, key, token, plugin-config or arbitrary-label field. A credential canary placed in the fixture inputs of I3.1c must be absent from every answer and evidence payload.
- Metric labels other than the Route and consumer already named are never exposed; counts are the I2 window-local counts.

## D8 — Cursor (I3 §8)

| Item | Frozen decision |
|---|---|
| Encoding | Unpadded base64url of canonical JSON (sorted keys, compact) `{"after": [consumer_id, route_id], "query_digest", "schema_version": "0.7", "snapshot_id", "v": 1}`. Opaque to clients. |
| `after` | The `(consumer.id, gateway_route.id)` of the last row **fully emitted** on the previous page. Rows are ordered by that pair, bytewise ascending, so the next page is the rows strictly after it. |
| `query_digest` | The D9 `normalized_query_context_digest` of the request (target, gateway, environment, window, consumer filter). `limit` is not bound, so a client may change page size between pages. |
| Validation | Not decodable, unknown `v`, or a malformed field: a **validation error**. Well-formed but `query_digest` differs from the request's: `CURSOR_QUERY_MISMATCH`. `snapshot_id` is not the current snapshot (including after any unrelated import): `SNAPSHOT_NOT_AVAILABLE`, the client restarts explicitly (I3 §8). |
| Pages | A page is `PARTIAL` with `MORE_ROWS_AVAILABLE` iff rows remain after it; the last page carries no `next_cursor` and no such code. Within one snapshot, a client that passes server-issued cursors back unmodified sees no row duplicated or lost across a boundary (D8 integrity below). |
| Integrity | The cursor is a **position token, not an integrity-protected capability**, the same as the v0.6 locality cursor. It is not signed: AIP is stateless and deterministic and holds no server secret, and an unkeyed digest over the payload would add nothing because a client can recompute it. A client that decodes the cursor and substitutes a different well-formed `after` simply starts its continuation at that position. This is bounded: the rows still come from the same snapshot and the same query context (checked by `snapshot_id` and `query_digest`), only rows of the selection are ever returned, and the read-only API already returns any of those rows to a client that asks for them. It can therefore skip rows only for the client that forged the position. The no-duplicate/no-loss guarantee is for unmodified server-issued cursors. `after` must still be a well-formed `(consumer_id, route_id)` pair, otherwise it is a validation error. A keyed (MAC) cursor would need a server secret and a key lifecycle and is a reviewed amendment if a deployment ever needs one. |
| Authority | A cursor grants no access and attests no evidence. |

## D9 — Evidence refs and the evidence mode (I3 §9)

**Query-context digest.** `normalized_query_context_digest` = lowercase hex SHA-256 of the canonical JSON (sorted keys, compact, UTF-8, `ensure_ascii` false) of `{"consumer_id": <string or null>, "environment", "gateway_instance_id", "target": {"id", "kind"}, "window_end", "window_start"}`. Page position, `limit` and `snapshot_id` are not part of it.

**Ref.** `api-evidence:<sha256 hex of ld(snapshot_id, normalized_query_context_digest, evidence_kind, *sorted internal supporting ids)>`, where `ld` is `app.common.encoding.length_delimited` over the UTF-8 parts and the supporting ids are distinct and sorted bytewise. The ref is deterministic, opaque and snapshot-bound; the answer never exposes the internal ids.

**Kinds and supporting ids** (frozen; the sanitized payloads are the closed allow-lists below):

| `evidence_kind` | Internal supporting ids | Sanitized payload (only these fields) |
|---|---|---|
| `CONFIGURED_ACCESS` | the `GatewayConfiguredAccess` id of the pair and its `GatewaySourceEvidence` id | `gateway_instance_id`, `environment`, `source_revision`, `consumer {id, source_name}`, `gateway_route {id, source_route_id}`, `rule_kind`, `polarity`, `scope` |
| `MEASUREMENT_WINDOW` | the `MeasurementWindow` id and its `MeasurementEvidence` id | `source_instance_id`, `gateway_instance_id`, `environment`, `window_start`, `window_end`, `apisix_version`, `start_settled`, `end_settled`, `no_restart`, `start_stable_seconds`, `end_stable_seconds`, `valid`, `reasons[]`, `evidence_type`, `extract_digests {start_sha256, end_sha256}` |
| `ROUTE_OPERATION_RECONCILIATION` | the `GatewayRoute` id and the `MeasurementMappingEntry` ids that name the Route as `route_operation` | `gateway_route {id, source_route_id}`, `outcome` and `operation_id?` (the I2 `route_operation` result), `contract_version_reconciliation?` and `contract_version_id?` (the I2 contract-chain result, present only for a `RESOLVED` Operation), `mapping_entries[]` of `{operation_id}` (the explicit entries naming the Route, sorted, distinct), `rule {rule_id, rule_version}` |
| `TARGET_SERVICE_RECONCILIATION` | the `GatewayRoute` id, the Gateway Service id if any, and the mapping entry ids for the Route/Service target | `gateway_route {id, source_route_id}`, `outcome` and `service_id?` (the I2 `target_service` result), `mapping_entries[]` of `{target, service_id}` (`target` ∈ `ROUTE`, `GATEWAY_SERVICE`), `labels[]` of `{carrier, service_id}` (the raw `aip/service` values on the Route and on its Gateway Service; `carrier` ∈ `ROUTE`, `GATEWAY_SERVICE`), `rule {rule_id, rule_version}` |
| `QUALIFICATION_LIMITATIONS` | the `GatewayRoute` id, the `MeasurementWindow` id and the `MeasurementLimitation` ids of the Route (if any) | `gateway_route {id, source_route_id}`, `coverage`, `codes[]`, `window_valid` |

**Provenance boundary (I3 §2).** The two reconciliation kinds expose only what the frozen I2 snapshot already carries: the final I2 outcome and ids, the raw explicit mapping entries and `aip/service` label values that exist as snapshot facts, and the rule id/version. They state **which facts are present, not which one produced the outcome**: I2 does not persist or project a reconciliation basis (for example whether the exact-URI fallback applied), and deriving it would re-run part of the I2 rule in I3. No `basis` and no derived count is exposed. If the product later needs the basis, that is an explicit I2 handoff amendment, not an I3 reconstruction.

A row carries refs for `CONFIGURED_ACCESS` (iff `CONFIGURED_ACCESS_ESTABLISHED`), `MEASUREMENT_WINDOW`, `ROUTE_OPERATION_RECONCILIATION`, `TARGET_SERVICE_RECONCILIATION` and `QUALIFICATION_LIMITATIONS` (iff the Route has limitations). The same refs are reachable without a row through `window.evidence_refs` and `selected_routes[].evidence_refs`.

**Evidence mode.** The service reacquires the requested exact snapshot, deterministically rebuilds the finite map `ref → sanitized payload` for the resubmitted context from the same I2 sections, and resolves only refs in that map. There is no server-side ref history and no direct internal-id lookup. A forged ref, a ref minted under another snapshot, and a ref minted for another target/gateway/window/consumer-filter context are all simply absent from the map and are indistinguishable (`NOT_RESOLVED`); this is intended. The `data` is `{request_context, entries[]}`, one entry per requested ref sorted by ref: `{ref, status, kind?, evidence?}` with `status` ∈ `RESOLVED`, `NOT_RESOLVED`; `kind` and `evidence` only when `RESOLVED`.

The generic `get_evidence` is unchanged, and no `:Evidence` node, `SourceType` or public evidence endpoint is widened.

## D12 — Representation details of the published schemas (I3.1b)

These settle choices the models in `app/architecture_intelligence/api_usage_contracts.py` and the files under `schemas/architecture_intelligence/v0.7/` had to make. They only represent D1–D11; none changes their meaning.

| # | Detail |
|---|---|
| D12.1 | **Envelope.** `data` is null if and only if the answer is a refusal (D6). A refusal carries exactly one code: query ∈ the five refusal codes, evidence ∈ the first four. A refusal code never accompanies data. Both directions are validators and a schema if/then keyed on the code and `mode`. |
| D12.2 | **Evaluated `NOT_ANSWERED`.** Query: iff `NO_ROUTE_SELECTED` is among the codes, and the answer carries data. If the window is also invalid the codes are `{NO_ROUTE_SELECTED, WINDOW_NOT_VALID}`. Evidence: iff no ref resolved (`EVIDENCE_REF_NOT_RESOLVED`). `limitations` is exactly the set the data implies (`MORE_ROWS_AVAILABLE` ⇔ `page.next_cursor`; `WINDOW_NOT_VALID` ⇔ `window.valid = false`; `COVERAGE_UNKNOWN` ⇔ a selected Route is `UNKNOWN_COVERAGE`; `NO_ROUTE_SELECTED` ⇔ no selected Route), sorted, one per code. |
| D12.3 | **Free text.** A limitation `message` is any non-empty string (I3.2 chooses deterministic text); it carries no request value. |
| D12.4 | **Tokens.** Ids that D3 does not give a stricter form (`source_name`, `source_route_id`, source and rule ids, contract ids) are opaque tokens: non-empty, no whitespace or control characters. `gateway_instance_id` and `environment` use the existing environment pattern (≤ 256 / ≤ 128). The interaction id is `observed-consumer-interaction:owned:<64 hex>`. |
| D12.5 | **Window and Routes.** `window.valid` ⇔ no reasons. A Route is `SUFFICIENT_FOR_ZERO` ⇔ it has no limitations, and has evidence refs ⇔ it has limitations. A row carries its Route's coverage, limitations and `source_route_id` unchanged. |
| D12.6 | **Row truth-table guards** (the I2 §9.2 table, so a malformed answer cannot contradict I2): `OBSERVED_USAGE` needs a positive upstream count; `MEASURED_ZERO` needs a zero count, `SUFFICIENT_FOR_ZERO` coverage and `CONFIGURED_ACCESS_ESTABLISHED`; `USAGE_UNESTABLISHED` has no positive count; the two counts are present together or absent together; counts are present exactly when the window is valid, and an invalid window establishes no usage. |
| D12.7 | **Associations.** `api.operation_id` and `contract_version_reconciliation` ⇔ the Operation is `RESOLVED`; `contract_version_id` ⇔ the version is `RESOLVED`; `application_service.service_id` ⇔ `RESOLVED`. `association_summary` is absent for `GATEWAY_ROUTE`, otherwise carries exactly the chain of the target kind, and its `resolved_to_target` equals the number of selected Routes. A `GATEWAY_ROUTE` target selects exactly that Route. |
| D12.8 | **Rows and pages.** Rows are sorted and distinct by `(consumer.id, gateway_route.id)`, each on a selected Route of the requested gateway, matching the consumer filter if given; `page.returned` equals the row count; `rows` ≤ 200. `page.limit` echoes the applied limit; `limit` is not part of the cursor binding or of `request_context`. `next_cursor` must decode and be bound to the answer's `snapshot_id` and to the D9 query-context digest of `request_context`. |
| D12.9 | **Evidence payloads.** Five closed models, discriminated by `kind` inside `evidence`; an entry's `kind` must equal its payload's. Internal supporting ids appear in no model. The reconciliation payloads carry only D9's provenance-bounded fields. |
| D12.10 | **Codes.** The ten `GWM_*` window and coverage codes are one closed enum for rows, Routes and evidence; `window.reasons` use its four-member window subset. Both are mirrored by value from the I2 constants and a parity test pins them. |
| D12.11 | **Helpers.** The module also holds the two frozen D9 derivations (`query_context_digest`, `evidence_ref`) and the D8 cursor codec, as pure functions; a known-answer test recomputes them with the standard library only. |
| D12.12 | **What the schema cannot express** (sortedness of non-string arrays, cross-field rules D12.2 beyond the code sets, D12.5–D12.8, cursor decoding) is enforced by Pydantic and tested as Pydantic-only. |
| D12.13 | **Ref identity.** Every evidence kind's supporting-id set contains the id that distinguishes its payload, so two payloads in one context never share a ref. In particular `QUALIFICATION_LIMITATIONS` includes the canonical `GatewayRoute` id: I2 stores a `MeasurementLimitation` only for broken series, so most Route coverage limitations (`GWM_ROUTE_COVERAGE_ABSENT`, `GWM_CONSUMER_LABEL_DISABLED`, `GWM_ROUTE_PROMETHEUS_DISABLED`, `GWM_UNATTRIBUTED_UPSTREAM`, and the window reasons) have no carrier, and the window id alone would give every Route the same ref. |
