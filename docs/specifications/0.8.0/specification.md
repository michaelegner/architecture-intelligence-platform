# AIP v0.8 — Binding Picture Showcase

**Status:** Released in [`v0.8.0`](../../release-validation/v0.8.0-release-record.md) (2026-10-28), from Draft 0.5  
**Target:** `v0.8.0` (demonstration release)  
**Baseline:** published and verified `v0.7.2`, plus the doctrine pivot [#635](https://github.com/michaelegner/architecture-intelligence-platform/pull/635).  
**Scope authority:** [ROADMAP.md — v0.8](../../../ROADMAP.md#v08--binding-picture-showcase-shipped-demonstration-release) and the [product doctrine](../../product-doctrine-and-strategic-direction.md)

## 1. Promise

v0.8 demonstrates the **binding picture** on Sokol111 to a CTO or an enterprise architect. It is
built around one real finding.

**The finding.** Sokol111's documented architecture
([`platform-overview.md`, `product-update-flow.md`](https://github.com/Sokol111/ecommerce-workspace/tree/f6b4c1ce723cb3be83eda73d74b2bacb9c584f17/docs/architecture),
workspace commit `f6b4c1c`) says that Catalog Management publishes product and category events to
Storefront. The frozen broker evidence C1
([`kafka-consumer-state.json`](../0.7.2/i2-evidence/sokol111/c1/kafka-consumer-state.json),
2026-10-21T17:53:57Z) shows more:

- Catalog and Image consume `tenant.tenant.events` from Store Provisioning;
- Product Query and Category Query consume `catalog.attribute.events` from Catalog Management.

The documents name none of these bindings. A migration planned from the documents would bridge only
the product and category topics. The expected consequence is that new shops no longer reach the moved
context and attribute changes no longer reach the storefront: every service wires a tenant-event
consumer (`NewKafkaConsumerModule()` from `ecommerce-tenant-service-api`, in each service's
`internal/infrastructure/fxconfig/module.go`), and the query services consume attribute events. Only
the functional test (§4.4) establishes behaviour; AIP does not.

**Demonstration question:**

> **When Catalog Management moves from Redpanda to Apache Kafka, which bindings cross its boundary,
> which of them are declared, which does the evidence establish, and how does a coding agent use that
> picture to plan and carry out the move?**

**What is demonstrated:** an integrated, attributable comparison of declared architecture and
qualified Current State, available to humans and agents, before and after an AI-assisted change.

**What is not demonstrated:** that this comparison saves effort in a real organisation. That is the
later target-customer validation ([doctrine §8](../../product-doctrine-and-strategic-direction.md#8-product-validation)).
Source code and configuration can also reveal the tenant consumers; AIP's contribution is the
comparison with provenance, not exclusive knowledge.

## 2. Constraints

- **Demonstration release** ([ROADMAP Versioning](../../../ROADMAP.md#versioning)): the new promise,
  assessment and projection semantics are experimental and do not become a v1.0 contract.
- The six existing tools, REST parity and all v0.7.1 semantics stay unchanged, except the schema
  field descriptions for `destination_id` and `broker_id` on `get_destination_consumers`.
- AIP stays read-only. No manufactured evidence. Partial and unresolved results stay visible.
- **Build no more migration infrastructure or AIP semantics than the demonstration needs.**
- Long runs are staged so that each stage fits one daily usage window, with a checkpoint between
  stages.

**Disclosures** (shown in the report and the release notes): the EventCatalog and its owners are
generated for the showcase; catalog entries count as confirmed promises by assumption; the topic
inventory, the producer and Service declarations, and the extended group → Service mapping are
authored from source and configuration; the
target cluster is a local Apache Kafka standing in for a managed platform.

## 3. Inputs and declaration semantics

### 3.1 EventCatalog generation rule

The EventCatalog is generated by a script from the two documents at `f6b4c1c`. The rule is fixed in
this specification before any assessment runs:

1. **Domains** are the documented lifecycle groups: Store Provisioning ("Launch a store": Tenant),
   Catalog Management ("Manage products": Catalog, Image), Storefront ("Shop": Product Query,
   Category Query). Owners are illustrative team names.
2. A diagram node that names several services (for example "Product and Category Query Services")
   yields one **service entry** for each named service.
3. An arrow yields a `sends` or `receives` entry **only if it names both a service endpoint and an
   event** (a type or a family). Arrows that name no event (for example
   `broker -->|build projections| readModels`) yield no entry, for any service of the node.
4. An arrow from a service to the broker yields a `sends` entry; an arrow from the broker to a
   service yields a `receives` entry.

Document labels resolve through this fixed lookup; the script interprets nothing else:

| Document label | Event type or family | Topic (`TopicFor()`) |
|---|---|---|
| "TenantUpdated event" | `TenantUpdated` | `tenant.tenant.events` |
| "Product and category events" | product events family; category events family | `catalog.product.events`; `catalog.category.events` |
| "ProductUpdated event" | `ProductUpdated` | `catalog.product.events` |
| "ProductImagePromoted event", "image promotion event" | `ProductImagePromoted` | `catalog.product.events` |

Result:

| Service | `sends` | `receives` |
|---|---|---|
| Tenant | `TenantUpdated` | — |
| Catalog | product events, category events, `ProductUpdated` | — |
| Image | `ProductImagePromoted` | `ProductUpdated` |
| Product Query | — | `ProductUpdated`, `ProductImagePromoted` |
| Category Query | — | — |

The generated catalog is committed together with its SHA-256 digest and the script.

### 3.2 Promise semantics

- Each catalog entry counts as a **confirmed promise** of the owner the catalog names. This is a
  disclosed demonstration assumption, not an owner's act.
- A promise is scoped to the environment, not to a broker. It is resolved on every broker in capture
  scope, and assessed there separately.
- The documents are **not** complete promise coverage. A binding with no catalog entry is
  **unresolved on the promise side** and is shown as "observed, undeclared". It is never "observed,
  not promised" ([doctrine §4.3](../../product-doctrine-and-strategic-direction.md#43-assessment-is-locally-made)).

### 3.3 Current-State inputs

- **Topic inventory, producers and Services:** service-level AsyncAPI declarations, one per Service
  and broker, derived from `TopicFor()` in each `*-service-api/pkg/events/topics.go` (D7, D8). A
  Service declares `publish` on a topic that its own API maps, on the broker that it writes to. A topic
  whose writer on a broker is not a Service is declared there without operations. Services that
  publish nothing have a service-only declaration. No declaration names a consumer. They are declared
  Current-State evidence of Topic identity, producers and Services, not promises. Without the Topics,
  AIP does not persist an attachment (`KAFKA_TOPIC_NOT_DECLARED`,
  [v0.7.1 I1 contract §6](../0.7.1/i1-kafka-source-contract.md)). Details:
  [I1 §4](i1-declared-side-and-inventory.md#4-declared-current-state-d7-d8).
- **Group → Service mapping:** the existing mapping (Image, Product Query) is extended with Catalog
  and Category Query, from `default-group-id` in `ecommerce-infrastructure` (`07c0599`)
  `environments/*/values/*.yaml`. One mapping artifact per broker.
- **Broker evidence:** `aip-kafka-consumer-state/1` captures. They establish each group's state and
  its attached members with their topic assignments, per broker and at capture time. They establish
  no offsets, no lag, no producers and no event-type handling.

### 3.4 Event level and topic level

The report shows one chain per binding. Each link keeps its provenance:

> declared event relationship (catalog) → resolved Topic (`TopicFor()`, then the inventory Topic id
> of that broker) → qualified attachment (capture + group → Service mapping)

Assessment is made per **consumer Service × Topic × broker**. Event types are listed under it as
declared only. An attachment never proves that an event type was handled or processed. The producer
side has declared evidence only.

## 4. Migration wave 1: Catalog Management, Redpanda → Apache Kafka

### 4.1 Topology

- **Moves to Kafka** (`kafka:sokol111-kafka`): Catalog, Image.
- **Stays on Redpanda** (`kafka:sokol111-local`): Tenant, Product Query, Category Query, UIs.
- **Topic authority after the wave:** `catalog.product.events`, `catalog.category.events` and
  `catalog.attribute.events` live on Kafka, because all their producers move. They are mirrored
  Kafka → Redpanda (flow B). `tenant.tenant.events` stays on Redpanda and is mirrored
  Redpanda → Kafka (flow A).
- **No loops:** each topic is mirrored in exactly one direction. The MirrorMaker 2 allow-lists of
  flows A and B are disjoint, and the runbook checks this. The identity replication policy keeps
  topic names; it is safe only because no topic is mirrored both ways.
- **The mirror is an intermediary** (doctrine §4.2). Its promises come from its configuration. AIP
  does not observe it directly; this is a stated limit.

### 4.2 Cut-over protocol

Three kinds of check are never conflated:

- *replication caught up:* for every source partition of the topic, the mirror's committed source
  position (MM2 source offsets for that partition) equals the source end offset. This is source-side
  replication progress. It never compares end offsets across clusters: flow B writes into Redpanda
  topics that already hold history, and offsets on the two clusters do not share one coordinate
  system;
- *consumer caught up:* the broker tool shows lag 0 for a named group on a named topic;
- *application behaviour verified:* the functional test (§4.4) passes.

| Step | Action | Precondition to continue |
|---|---|---|
| 1 | Kafka up; `catalog.*` topics created empty on Kafka; flows A and B configured, both stopped | allow-lists disjoint |
| 2 | Start flow A (tenant, Redpanda → Kafka) with `emit.checkpoints.enabled` and `sync.group.offsets.enabled` set explicitly (the latter is off by default) for `ecommerce-catalog-service` and `ecommerce-image-service` | *replication caught up* on `tenant.tenant.events` |
| 3 | Stop Catalog | *consumer caught up* for Image on `catalog.product.events` |
| 4 | Stop Image | Catalog and Image groups on Redpanda report zero live attachment (`Empty` or `Dead`) |
| 5 | Drain | *consumer caught up* for the **remaining** Redpanda consumers only: Product Query (`catalog.product.events`, `catalog.attribute.events`), Category Query (`catalog.category.events`, `catalog.attribute.events`) |
| 6 | Offset hand-off, per group and partition of `tenant.tenant.events`: read (a) the final committed offset on Redpanda; (b) the latest MM2 checkpoint for that group and partition; (c) the committed offset installed on Kafka | the checkpoint's upstream offset equals (a), and (c) equals the checkpoint's downstream offset. Otherwise wait for the next sync; stop if (c) is missing or differs from the checkpoint |
| 7 | Start flow B (`catalog.*`, Kafka → Redpanda) | — |
| 8 | Start Catalog and Image on Kafka (Helm values point to the Kafka bootstrap) | both groups Stable on Kafka |
| 9 | Restart checks | *replication caught up* on flow B after new traffic; *consumer caught up* for Product Query and Category Query on Redpanda and for Catalog and Image on Kafka; AIP captures both brokers; *application behaviour verified* |

- **Offsets:** step 6 compares positions only inside one coordinate system: Redpanda offsets with
  the checkpoint's upstream offset, Kafka offsets with the checkpoint's downstream offset. MM2
  translation rounds down to the last offset-sync point, so the installed offset can be lower than
  the exact position. **Replay amount:** the records between the installed Kafka offset and the
  position that corresponds to the final Redpanda offset may be **reprocessed**. I3 measures this
  amount, or estimates it conservatively, from the recorded checkpoint, offset-sync and installed
  positions; if no bound can be established, it says so. `offset.lag.max` is MM2's resync threshold,
  not a guaranteed bound ([I3 §5](i3-two-broker-environment-and-live-captures.md#5-runbook-parent-42-steps-19)). An installed offset that differs from the checkpoint could
  skip records; step 6 stops on it. Sokol111's reset policy is `earliest`, so a missing installed
  offset would replay all tenant events; step 6 stops on that too. The spec states the
  duplicate-processing assumption; it does not prove idempotence. The functional test checks that
  reprocessing causes no error.
- **No duplicate `catalog.*` records:** the Kafka topics start empty, the producers are stopped
  before flow B starts, and the Redpanda history is drained first.
- **No lossless or exactly-once claim.** Rollback is an environment reset and a new run, not a
  migration feature.

### 4.3 Two-broker capture rules

- The **Redpanda** registration keeps the same allow-list before and after the wave (Catalog, Image,
  Product Query, Category Query). The wave is therefore not a scope change. After the wave, the
  expectation for Catalog and Image follows the qualified broker reading: `Empty` or a
  broker-reported `Dead` both mean zero live attachment ([v0.7.1 I1 contract §4](../0.7.1/i1-kafka-source-contract.md)).
  If a group cannot be described, the capture is incomplete (`KAFKA_CAPTURE_INCOMPLETE`): stop, and
  never turn an acquisition failure into a detachment claim. A deliberate scope change would be a configuration change, never evidence of
  detachment ([v0.7.1 I1 contract §5](../0.7.1/i1-kafka-source-contract.md)).
- The **Kafka** registration has its own broker id, the allow-list {Catalog, Image} and its own
  group → Service mapping. MirrorMaker 2's internal groups are outside both scopes.
- Each broker has its own Topic ids, because the broker is part of the id. The projection shows both.
  It links them only through the declared mirror configuration and never merges them into one Topic.

### 4.4 Proof boundaries

| Claim | Established by |
|---|---|
| group state and topic assignments per broker, before and after, attributed to Services | AIP |
| offsets, lag, replication progress | broker tools (`rpk`, `kafka-consumer-groups`), stored as ground truth |
| migrated behaviour works | functional test after the cut-over: (1) create a shop, then a product with an image in it; Product Query returns the product with its current image URL (tenant, product and image-promotion flows); (2) update a category; Category Query returns the change (category flow); (3) update an attribute definition; Product Query and Category Query return the change (attribute flow) |

- **Proof A, plan answer key:** before the agent run, the expected wave plan is written down: the
  mirrored topics and their directions, the changed Helm values, the cut-over checks. It is a different
  key from the after-wave capture reference `expected-after.json`, which scores Proof C (D16).
- **Proof B, citations:** the agent's plan cites the AIP claims it relies on. The report checks that
  each cited claim exists and supports the binding behind the plan item. AIP evidence supports the
  binding, never the correctness of the migration mechanism; the mechanism needs its own
  implementation justification (D16).
- **Proof C, live run:** the wave is carried out and AIP captures both brokers again.

## 5. AIP capabilities (experimental)

- **EventCatalog source adapter:** reads domains, owners and `sends`/`receives` into promises and
  Bounded Context membership, with provenance (file, digest).
- **Promise record:** kept apart from Current State. Neither manufactures the other.
- **Per-binding assessment:** the doctrine §4.3 statuses, at the §3.4 level.
- **Crossing-binding projection:** for a selected Bounded Context, across both brokers, with one row
  per consumer Service × Topic × broker (§3.6).
- **One experimental MCP tool and its REST twin** for the binding picture. Every field has a
  description that says which identifier it expects. The tool exists only when the setting
  `experimental.binding_picture` is on; the default tool list stays six, and the hosted and showcase
  profiles turn it on (D11).
- **Field descriptions** for `destination_id` and `broker_id` on `get_destination_consumers`.

**Before/after comparison is report-level only.** The report compares two independently qualified
snapshots and shows each with its own observation context and limits. It is not an AIP semantic
capability.

## 6. Demonstration

**Agent.** The coding agent reads the binding picture through MCP. It writes the wave plan, the Helm
value changes and the MM2 configuration, then carries out the cut-over (§4.2). Its plan cites the AIP
claims it relies on. It supports the story; it is not the centre of it.

**Report.** One generated HTML report over AIP's interfaces, in four parts:

1. **Before:** Catalog Management's bindings on Redpanda. No Kafka capture exists before the wave, so
   this part covers one broker.
2. **Insight:** documented compared with established; the undeclared tenant and attribute bindings
   highlighted, with the chain of §3.4 for each.
3. **Agent:** the wave plan, with each item linked to the AIP claim it cites.
4. **After:** the binding picture on both brokers: what is now established, what stays unresolved,
   and the external checks of §4.4 shown separately from AIP's claims.

The report is not a visualisation product.

- **Outcome:** Sokol111 local environment with Redpanda and Apache Kafka (KRaft), MM2 flows A and B,
  AIP captures and broker-tool ground truth before and after a scripted cut-over, the functional

  the captures meet §4.3 and reproduce §3.6; every check of §4.4 is recorded. Runs are staged with checkpoints.
