Before an AI agent changes a distributed system, do we understand the bindings that change relies on?

Sokol111 is a multi-tenant e-commerce system. Its services exchange events through a Redpanda broker. The modernization step shown here moves one bounded context, Catalog Management (the Catalog and Image services), to Apache Kafka, with MirrorMaker 2 bridging the two brokers. A move like this is safe only if every binding that crosses the boundary of the moving context is known before the move and still holds after it.

The flow of this page follows that question. First the bindings, then what is declared and what the evidence establishes, then the plan that a coding agent built on that picture, then what the evidence establishes after the move. AIP is read-only: it gives understanding of the bindings, not power over the system.

1. Before: the boundary and the bindings that cross it

(1) What boundary changes?

Catalog Management moves from Redpanda (kafka:sokol111-local) to Apache Kafka (kafka:sokol111-kafka). Store Provisioning (Tenant) and Storefront (Product Query, Category Query) stay on Redpanda. Before the move, only Redpanda has a capture.

3. Agent: why the bindings matter for this move

(4) Why do they matter for the migration?

A coding agent planned and carried out the move. It read the binding picture through AIP's MCP interface. AIP establishes the bindings. The agent derives the migration requirements, then chooses and carries out the plan. Independent evidence establishes what the migration achieved.
