# Sokol111 replay package (v0.7.2 I2.1)

These are the frozen inputs for the hosted Sokol111 dataset ([v0.7.2 spec](../../specification.md) §4). The committed bytes are the inputs: re-running the environment would not reproduce them, because member ids, hosts and T would differ. Digests are in [`SHA256SUMS`](SHA256SUMS) and the capture times in [`replay-metadata.json`](replay-metadata.json).

## Scenario

The change is a new field in `ProductUpdatedEvent`, which `ecommerce-catalog-service` publishes on the Kafka topic `catalog.product.events`. The question is which Services consume that topic, and how sure we can be. From source and configuration, the candidate consumers are `ecommerce-product-query-service` and `ecommerce-image-service`: each has a `catalog-events` consumer on the topic under its own `default-group-id`. The scenario and revisions are the ones frozen in v0.8 Round 4 ([freeze](../../../../real-world-validation/v0.8.0/round4-sokol111-freeze.md)). Round 4 rejected Sokol111 because AIP could not attribute Kafka consumer groups then; v0.7.1 can.

## Ordering

The git history shows the order:
1. `expected.json` and `EXPECTED.sha256`, covering both C1 and C2, were committed (`116ec4f`) before the environment was started.
2. The captures were taken afterwards.

G1 and G1' match exactly (same members and assignments), and C1 holds exactly those assignments. C2's group states are the G2 states. Real traffic committed the offsets, and `--reset-offsets` was never used. The traffic came from the system's own flows:
- a tenant registered through the tenant service's `RegisterTenant` RPC, exactly as the platform UI's server does it (an S2S client-credentials token of the local Logto, with credentials generated by the environment's own `logto-seed`);
- the tenant service's own seeder job, which created the demo catalog: 60 events on `catalog.product.events`.

No consumer was started by hand, and no Sokol111 source file changed.

## Environment adaptations (disclosed)

All of these are local-host compatibility changes; none touches a service, a contract or a Helm chart.

- **k3d config** ([`raw/k3d-cluster.adapted.yaml`](raw/k3d-cluster.adapted.yaml)): the author's hard-coded CA-bundle host path becomes this checkout's `certs/` path. Also, `--kubelet-arg=fail-cgroupv1=false` is added, because this WSL2 host runs cgroup v1, which k3s v1.35's kubelet refuses by default; the first start failed on exactly that.
- **`compose/logto.yml`** ([`raw/infrastructure-local.diff`](raw/infrastructure-local.diff)): `network: host` is dropped from the `logto-seed` build. Docker Compose v5.6 always builds through `bake`, which refuses host networking without `--allow=network.host`.
- **Tilt** ran only the Go services and their infrastructure: `tilt up ecommerce-tenant-service ecommerce-tenant-service-seeder ecommerce-catalog-service ecommerce-product-query-service ecommerce-image-service ecommerce-category-query-service`. It did not run the Nuxt UIs. MinIO and imgproxy were therefore not started. The seeder's image uploads failed, and the products it created without an uploaded image were created disabled. That doesn't affect Kafka attachment.
- **Isolation:** `KUBECONFIG`, `MCP_KUBECONFIG` and the Helm homes pointed to a scratch directory. Everything this run created was removed afterwards: the k3d cluster and registry, the Compose stack and its volumes, and the image it built. The upstream base images it pulled remain in the local Docker cache.

## Commands

Each step is recorded in `raw/NN-*.txt` (stdout), `raw/NN-*.meta` (UTC, command, exit code) and `raw/NN-*.err` (only when stderr was non-empty). Broker commands ran in the `redpanda` container. The files are verbatim except for one edit made after recording: the local checkout prefix in the `--out` paths of steps 10 and 28 (`.meta` and `.txt`) became `<AIP checkout>/`, and in `raw/k3d-cluster.adapted.yaml` the scratch path became `<infrastructure checkout>/`.

**Setup effort:** about 40 minutes, from `make init` at 17:16Z to C2 at 17:56Z. That includes three host adaptations (cgroup v1, Compose `bake`, and one restart of Tilt), all made inside the 3-hour time box.

| Files | Step |
|---|---|
| 01–05 | **G1**: `rpk group list`, then `rpk group describe <group>` for each of the four groups |
| 06–08 | `rpk topic describe catalog.product.events`, `rpk version`, broker image |
| 10 | **C1**: `KAFKA_BOOTSTRAP_SERVERS=localhost:9092 PYTHONPATH=. uv run --with confluent-kafka==2.16.0 python harness/kafka-capture/capture.py --broker-id kafka:sokol111-local --environment local --group ecommerce-catalog-service --group ecommerce-category-query-service --group ecommerce-image-service --group ecommerce-product-query-service --out c1/kafka-consumer-state.json` |

| 20 | `kubectl -n dev scale deployment/ecommerce-image-service --replicas=0` |
| 21–25 | **G2**: list and describes; the Image group is `Empty` with committed offsets |

The tenant registration (17:48:59Z, `REGISTRATION_STATUS_COMPLETED`) and the seeder job (complete 17:53:07Z) ran before step 01. The token was never printed or recorded.

## Replay

`tests/integration/test_v072_i2_sokol111_replay.py` is in the qualification tier.
- It imports C1 and then C2 through `run_all_configured_sources`.
- It compares each answer with `expected.json` on the service, REST and negotiated MCP.
- It resolves the C1 evidence against the frozen capture and mapping bytes.
- It checks that replaying C2 a second time changes nothing.
